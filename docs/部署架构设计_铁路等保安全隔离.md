## 架构总览

本架构完全按照铁路行业等保安全要求设计，核心原则：**数据不出内网、算力集中部署、通信无线受控、导出有线隔离**。

## 一、眼镜与挎包通信方案 (BLE 1:1)

### 通信方式选型：BLE 5.0 LE Secure Connections

| 选型维度 | BLE 5.0 | WiFi Direct | LoRa | UWB |
|----------|---------|-------------|------|-----|
| 通信距离 | 可控 (TX 功率调节) | 30-100m (不可控) | 1-15km (过长) | 10-30m |
| 1:1 配对 | 原生支持 | 需额外配置 | 广播模式 | 支持 |
| 功耗 | 极低 (CR2032可驱动) | 高 | 低 | 中 |
| 抗干扰 | 自适应跳频 (79 信道) | 固定信道 | 窄带 | 超宽带 |
| 加密 | AES-128 (LE SC) | WPA3 | AES-128 | AES-128 |
| 铁路频段合规 | 2.4GHz ISM (免许可) | 2.4/5GHz | 470-510MHz (需许可) | 6-8GHz |
| 实时性 | <100ms | <50ms | 1-10s | <10ms |
| 带宽 | 1-2 Mbps (MTU 247B) | 54-433 Mbps | 0.3-50 kbps | 0.5-1 Mbps |

**选型结论：BLE 5.0 LE Secure Connections**

理由：
1. 通信距离可通过 TX 功率精确控制到 10 米以内
2. 自适应跳频扩频 (AFH) 抗铁路电磁干扰（牵引回流、接触网电弧）
3. 2.4GHz ISM 频段免许可，无需向铁路无委申请频率
4. 功耗极低，适合眼镜端电池供电
5. LE Secure Connections 提供 AES-128 加密配对

### BLE 安全配置

| 参数 | 配置值 | 说明 |
|------|--------|------|
| `max_connections` | 1 | 严格 1:1，仅允许一副眼镜 |
| `tx_power_dbm` | -6 | 控制通信距离 ≤10m（铁路金属环境衰减更快） |
| `pairing_mode` | le_secure | LE Secure Connections (ECDH 密钥交换) |
| `encryption_key_size` | 16 | AES-128 加密 |
| `bonded_device_address` | 预绑定 MAC | 仅允许预绑定的眼镜连接 |
| `rssi_disconnect_threshold` | -85 dBm | 低于此值主动断连，防止远距离窃听 |
| `heartbeat_interval` | 5s | 缩短心跳，快速检测异常断连 |
| `heartbeat_timeout` | 15s | 超时自动断开重连 |

### 铁路频段合规说明

- **BLE 使用 2.4GHz ISM 频段 (2400-2483.5MHz)**，全球免许可使用
- 中国铁路沿线无线通信主要限制在 GSM-R (900MHz) 和 LTE-R (1.8GHz) 专用频段
- BLE 的 2.4GHz 与铁路专用通信系统频段不重叠，无干扰风险
- 自适应跳频 (AFH) 自动避开被占用的信道，进一步降低干扰

## 二、挎包与指定 PC/服务器的有线连接

### 连接方式

**USB 数据线直连** — 挎包终端通过 USB 数据线连接到指定 PC/服务器：

| 特性 | 配置 |
|------|------|
| 物理接口 | USB 2.0 Type-C (CM4 OTG) |
| 网络模式 | CDC-ECM (USB 网卡) |
| 挎包 IP | 10.0.0.1/24 (固定) |
| PC IP | 10.0.0.2/24 (DHCP from 挎包) |
| API 端口 | 9090 (仅绑定 10.0.0.1) |
| 串口调试 | CDC-ACM /dev/ttyACM0 |
| 隔离方式 | iptables 双向 DROP (USB ↔ 其他接口) |

### 数据传输方式

#### 方式 A：.dat 打包文件传输（主要方式）

挎包终端将数据打包为 `.dat` 二进制容器文件，PC 通过 USB 拷贝后用专业应用导入。

```
挎包端:  收集数据 → 计算 SHA-256 → 生成 manifest →
         HMAC-SHA256 签名 → 封装为 .dat → 存入 /exports/

PC 端:   USB 连接 → 挂载 → 拷贝 .dat → 专业应用导入 →
         验证 HMAC 签名 → 逐文件校验 SHA-256 → 解析数据
```

.dat 文件格式：
```
┌────────────────────────────────────────────────────┐
│ Header (64B)                                        │
│  Magic "RAIL" + Version 2 + 段偏移/大小             │
├────────────────────────────────────────────────────┤
│ Data 段                                             │
│  [PathLen][Path][FileSize][SHA256][Content] × N    │
├────────────────────────────────────────────────────┤
│ Manifest 段 (JSON)                                  │
│  导出ID + 类型 + 文件列表 + 元数据                  │
├────────────────────────────────────────────────────┤
│ Signature 段 (64B)                                  │
│  HMAC-SHA256 (hex)                                  │
└────────────────────────────────────────────────────┘
```

#### 方式 B：API 接口调用（后续开发）

PC 端专业应用通过 HTTP API 直接访问挎包数据（仅 USB 局域网）：

| 端点 | 方法 | 说明 |
|------|------|------|
| `/auth/pair` | POST | Token 配对认证 |
| `/exports/create` | POST | 创建 .dat 导出包 |
| `/exports/{id}/download` | GET | 下载 .dat 文件 |
| `/exports/{id}/verify` | GET | 验证完整性 |
| `/photos/list` | GET | 列出照片 |
| `/photos/{id}/download` | GET | 下载照片 |
| `/detections/list` | GET | 列出检测结果 |
| `/alerts/list` | GET | 列出告警 |
| `/health` | GET | 健康检查 |

## 三、更大算力分析部署

### 指定 PC/服务器算力架构

所有重型 AI 分析在指定 PC/服务器上进行，挎包终端仅负责实时轻量推理：

| 层级 | 设备 | 模型/任务 | 说明 |
|------|------|-----------|------|
| 边缘实时 | 挎包 CM4 | YOLOv8n (320x320) | 实时缺陷初筛，<500ms |
| 边缘轻量 | 挎包 CM4 | Phi-3-mini Q4 | 基础规程问答，离线 RAG |
| PC 精检 | 指定 PC | YOLOv8x (640x640) | 高精度缺陷复检，GPU 加速 |
| PC 大模型 | 指定 PC/服务器 | Qwen-72B / GPT-4 | 复杂推理、报告生成 |
| PC 全量RAG | 指定 PC/服务器 | Dify RAG (完整知识库) | 全量铁路规程、历史案例 |
| PC 多模态 | 指定 PC/服务器 | GPT-4V / Qwen-VL | 图文关联分析、异常研判 |

### 数据流转

```
巡检现场 (挎包端)
    │
    ├── YOLOv8n 实时检测 → 初筛结果 (存 SQLite + .dat)
    ├── Phi-3 基础问答 → 简单规程查询 (存 SQLite + .dat)
    ├── 照片/视频 → SD 卡存储
    └── 告警 → 实时 BLE 推送到眼镜
    
    │ USB 数据线连接
    ▼
指定 PC/服务器 (算力中心)
    │
    ├── 导入 .dat → 验证签名 → 解析数据
    ├── YOLOv8x 精检 → 对初筛结果进行高精度复检
    ├── GPT-4V/Qwen-VL 多模态 → 图文关联分析
    ├── Qwen-72B/GPT-4 → 生成巡检报告、异常研判
    ├── Dify RAG → 全量知识库检索 (含历史案例)
    └── PostgreSQL → 数据仓库持久化
```

## 四、数据安全隔离设计

### 安全等级矩阵

| 安全层级 | 机制 | 实现 | 等保对应 |
|----------|------|------|----------|
| 物理层 | USB 有线连接 | 仅物理数据线可触发数据传输 | 物理隔离 |
| 网络层 | iptables 防火墙 | USB ↔ 其他接口双向 DROP | 网络边界防护 |
| 接口层 | API 绑定 USB 网卡 | FastAPI 仅监听 10.0.0.1:9090 | 访问控制 |
| 认证层 | Token 配对 | 8位数字，TTL 30分钟，断开撤销 | 身份认证 |
| 传输层 | BLE AES-128 加密 | LE Secure Connections | 通信加密 |
| 完整性 | SHA-256 + HMAC | 逐文件哈希 + 清单签名 | 完整性校验 |
| 调试层 | 命令白名单 | 仅允许只读/安全命令 | 最小权限 |
| 审计层 | 日志记录 | 所有操作可追溯 | 安全审计 |
| 介质层 | .dat 二进制封装 | 非标准格式，需专用工具解析 | 数据保密 |

### 网络隔离拓扑

```
                    ❌ 无任何外部网络连接
                    ❌ 无 5G 模块
                    ❌ 无 WiFi 对外
                    ❌ 无蓝牙对外 (仅 BLE 1:1)

┌──────────────────────────────────────────┐
│           挎包终端 (CM4)                 │
│                                          │
│  内部数据区          USB 导出通道         │
│  ┌─────────┐        ┌──────────────┐    │
│  │ SQLite  │        │ usb0 10.0.0.1│◄──┼── USB 线 ── PC
│  │ 照片    │        │ API :9090    │    │             (10.0.0.2)
│  │ 模型    │        │ Token 认证   │    │
```

## 六、完整工作流程

### 日常巡检流程

```
1. 巡检人员佩戴眼镜 + 挎包开机
2. BLE 自动配对 (1:1, 预绑定 MAC)
3. 眼镜 OLED 显示 "已连接"
4. 巡检中:
   a. 语音 "拍照" → 挎包触发拍照 → YOLOv8n 实时检测 → 结果回显
   b. 语音 "规程查询" → Phi-3 离线 RAG → 答案回显
   c. 检测到缺陷 → 告警 BLE 推送 → 眼镜振动 + 显示
5. 巡检结束 → 数据存入 SQLite + SD 卡

6. 返回指定场所 → USB 连接 PC
7. 挎包 OLED 显示 Token
8. PC 专业应用输入 Token → 认证通过
9. 选择导出方式:
   a. 打包 .dat → PC 拷贝 → 导入验证
   b. API 调用 → 直接读取数据 (后续开发)
10. PC/服务器进行:
    a. YOLOv8x 精检 → 复核初筛结果
    b. GPT-4V 多模态分析 → 异常研判
    c. Qwen-72B 生成巡检报告
    d. Dify RAG 关联历史案例
    e. PostgreSQL 入库
11. USB 断开 → Token 自动撤销 → 挎包返回待机
```
